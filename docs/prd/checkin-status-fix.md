## 1. 一句话概述（What & Why）
将"是否已打卡"的判定口径从"以今天的自然日匹配 check_in 记录"修正为"以日程实例自身是否存在 check_in 记录"，避免用户跨天回看时已打卡日程被误判为未打卡，并防止同一实例被重复打卡。

## 2. 用户场景

### 正向场景
1. **跨天回看已打卡（核心修复）**：用户昨天对"晨跑 7:00"打过卡，今天打开应用切到昨日视图（或重复日程历史实例），应当看到该日程显示"已打卡"图标，且打卡按钮不可再次触发。
2. **当天首次打卡**：用户打开今天的日程列表，对一条今日尚未打卡的日程点击打卡按钮，系统记录成功并即时切换为"已打卡"状态。
3. **重复日程多天独立**：用户的"每日英语 8:00"是重复日程，周一已打卡，周二打开时该周二实例仍显示"未打卡"，可独立完成本日打卡，互不影响。

### 反向场景
4. **误连击防重复**：用户对同一日程实例在 1~2 秒内连续点击打卡按钮，系统只产生一条 check_in 记录，UI 提示"这条日程已经打过卡啦"。
5. **历史日程重复点击**：用户对昨日已打卡日程再次点击打卡按钮（极端情况下若仍可点），系统不应再写入新的 check_in，给出与场景 4 一致的提示。

## 3. 功能范围

### In Scope
- `ScheduleProvider.isCheckedIn(scheduleId)` 作为统一打卡判定入口
- `ScheduleProvider.checkIn()` 重复校验改为按日程实例
- `home_screen` 的 `_ScheduleCard` 使用新判定 + 失败提示语调整
- `isCheckedToday` 作为向后兼容别名，保持 today_overview_screen / schedule_detail_screen 旧调用可用

### Out of Scope
- 不改打卡数据模型（CheckIn / Schedule 字段）
- 不改课时扣减规则与课程类日程业务逻辑
- 不引入按"日"维度的打卡聚合统计（若未来需要"今日完成多少打卡"等聚合，再单独立项）
- 不涉及视觉风格调整、动效改动
- 不涉及打卡撤销/重置功能

## 4. 验收标准（G3/G4 判定依据）

> 编号即测试用例锚点，QA 可一一对应。

- **AC-01（历史已打卡显示）**：用户切换到昨日（或更早）已打过卡的日程，系统应当在卡片上展示"已打卡"图标态，且打卡按钮不再触发新的写入。
- **AC-02（同实例不可重复打卡）**：用户对同一日程实例点击打卡按钮第二次时，系统应当不写入新的 check_in，并通过 SnackBar 提示"这条日程已经打过卡啦"。
- **AC-03（重复日程跨天独立）**：用户的重复日程在 D1 已打卡，D2 的同名实例打开时系统应当显示"未打卡"，并允许独立完成 D2 实例的打卡。
- **AC-04（当天打卡流程不受影响）**：用户对今日尚未打卡的日程点击打卡按钮，系统应当成功写入 check_in，UI 立即切换为"已打卡"，无报错、无重复提示。
- **AC-05（课程类日程仍正确扣课时）**：用户完成课程类日程的首次打卡时，系统应当按既有规则正确扣减课时（仅在该实例首次成功 checkIn 时触发，不会因新判定逻辑而重复扣减或漏扣）。
- **AC-06（兼容旧入口）**：在 today_overview_screen 与 schedule_detail_screen 通过 `isCheckedToday` 调用时，系统应当返回与 `isCheckedIn` 完全一致的判定结果，不出现 UI 显示与数据状态不一致的现象。

## 5. 风险 / 依赖

- **R1（命名兼容路径）**：`isCheckedToday` 现保留为 `isCheckedIn` 的别名，名字仍带"Today"语义但实际不再按"今天"判断，存在认知误导风险。
  - **建议**：在下一次涉及 today_overview_screen / schedule_detail_screen 的迭代中，统一替换为 `isCheckedIn` 调用，并删除别名；删除前在代码注释中明确标注"deprecated, 仅做向后兼容"。
- **R2（数据迁移）**：旧版本写入的 check_in 记录均带 scheduleId，新逻辑直接复用，不需要数据迁移；但需 QA 在升级用户的真实数据上回归 AC-01 / AC-03。
- **D1（依赖）**：日程实例 ID 在重复日程展开时必须保证按天唯一（每天一个实例 ID），否则 AC-03 不成立。该假设来自现有日程模型，需 dev-agent 在 G3 自检中确认未被回归破坏。
